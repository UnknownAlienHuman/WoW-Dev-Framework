## Findings

### F01 — compatibility-report duplicate keys disappear before evidence validation

Priority: P1 correctness/security boundary. Code: [compatibility.rs lines 65–130](https://github.com/UnknownAlienHuman/WoW-Dev-Framework/blob/02d893cd3b9c9dd116a3330824b9764c3d5ab919/crates/wow-emmy/src/compatibility.rs#L65-L130).

`backend_identity_from_report` parses directly into `serde_json::Value`, then computes the semantic digest and interprets compatibility/source fields. Duplicate decoded object keys are already lost. A valid sealed report can be changed from `"status":"compatible"` to `"status":"incompatible","status":"compatible"`; the retained Value and semantic hash are unchanged. Escaped spellings such as `st\u0061tus` must have the same member identity.

This is ambiguity/conflict loss, **not a forged signature or demonstrated code execution**. The repository JSON checker already rejects duplicate keys, but it does not protect this external report-import boundary. W01 supplies a focused code change and negative/positive regressions; it remains uncompiled until its stated checks run.

### F02 — maintenance commands allocate before their input bounds

Priority: P1 resource safety. Code: `crates/wow-emmy/src/bin/wow-emmy-probe.rs:28`; `crates/wow-reference/src/bin/wow-reference-api.rs:68`, `wow-reference-topology.rs:78`, `wow-reference-source.rs:66,78,213`; inactive builder `src/lib.rs:251–265`.

`fs::read` loads the input before downstream format limits can reject it. A metadata check followed by unbounded read also fails to bound concurrently growing input. Enforce a limit on the opened reader, reading at most limit + 1 bytes and failing explicitly, before parsing. Preserve each format's existing budget; do not invent a generic host/filesystem capability in core. W02 owns the active maintenance paths; W07 owns the dormant app.

### F03 — production WoW rule execution remains unavailable

Priority: P1 functional blocker. Code: [local/projection.rs lines 330–382](https://github.com/UnknownAlienHuman/WoW-Dev-Framework/blob/02d893cd3b9c9dd116a3330824b9764c3d5ab919/crates/wow-service/src/local/projection.rs#L330-L382), `wow-rules/src/descriptor.rs:11`, `context.rs:289–295`.

The service executes the WoW rules only for `FIXTURE_PROFILE_ID`; other profiles receive `unsupported_rule_profile` / `rules.profile.supported` NotEvaluated. This is an honest limitation, not fake successful analysis, but it blocks the useful ordinary-project path. Do not simply remove the guard: the E0 rule context and reference partitions are fixture-specific. W03 binds real exact Reference/Library inputs; W04 adds capability-gated production policies while preserving fixture behavior and unsupported cases.

### F04 — the reference builder is dormant and does not implement its documented command contract

Priority: P1 functional blocker. Code: `apps/wow-reference-builder/Cargo.toml`, `src/lib.rs:12–16,208–247`; norm: [E1 application boundary](../crates/wow-service/e1/APPLICATION_BOUNDARY.md#cli-commands).

The source imports absent `ReferenceAdminExpectation`, `ReferenceAdminObjectId` and related service names and calls an absent `ReferenceAdminError::not_found`. It exposes status/validate/publish/read rather than the normative build/validate/rebuild-compare frontend and uses different exit classes. Workspace CI cannot establish that this inactive source compiles. Fix the service use cases first, then repair the thin frontend and explicitly update its workspace/CI inclusion. Do not expose raw storage APIs just to compile obsolete calls. W06/W07 own this seam.

### F05 — annotation persistence violates the declared dependency map

The active regular dependency `wow-annotations → wow-store` is absent from the manifest's allowed edges and from the normative dependency table. Literal-rendering edges have a documented exception; this persistence edge does not. This is not a cycle and not evidence the persistence code is fake. W05 must make an explicit reviewed ownership decision: justify a narrow typed persistence edge in an ADR and all registries, or relocate persistence orchestration behind an already allowed seam. Merely editing the allowed list to silence validation is not acceptance.

### F07 — project updates rebuild synchronously and have incomplete update semantics

Priority: P2 functionality/performance. Code: `wow-project/src/publication.rs:164–202`; norm: [update model](../crates/wow-project/UPDATE_MODEL.md#7-analyzer-batch-construction), [incremental invalidation](../crates/wow-project/e2/INCREMENTAL_INVALIDATION.md#cancellationfailure).

The update route rebuilds via `build_snapshot` with a newly false cancellation flag instead of an externally cancellable incremental update. An empty replacement-library vector also means retain previous libraries, so the current API cannot distinguish keep from explicitly clear. The latter is an API design gap to resolve against the owned contract, not an asserted failing existing acceptance test. W14 must define that distinction, preserve the old generation on failure and prove removed/stale facts do not survive.

## Work queue and execution policy

[WORK_QUEUE.md](WORK_QUEUE.md) is the compact queue index. Each linked draft PR carries its own complete task, code boundaries, exact normative sections, dependencies, acceptance checks and current state. Agents read the index plus their selected task and owner contracts, not every task at once.

The user's 2026-09-25 PR request authorizes these named task branches despite historical main-only instructions. This does not authorize force-pushes, automatic merges, disabling CI, source execution, new credentials or public releases. All PRs target `main`. Draft specification PRs initially add a task document, **not an implemented feature**. Continue implementation in that same branch; merge only with the stated code and evidence. Do not merge a task-only draft as feature completion.

Use distinct states: **specified → coding → code-written/unverified → focused-checks-passed → reviewed/merged → package-accepted**. A merged code slice is not automatically full E0/E1/E2 or launch acceptance. The W01 code is proposed, not compiler-verified. Leave R0/A0/A1/B0/V1 unchanged until their exact evidence closes.

Implementation dependencies in the queue are not blanket fixture gates. Ready independent branches may proceed in parallel, but only one worker owns a file/semantic seam at a time. Re-read remote heads before publication; incorporate prerequisites without force-pushing or discarding other contributors' work. Close a superseded task only with links to equivalent implementation and evidence.
